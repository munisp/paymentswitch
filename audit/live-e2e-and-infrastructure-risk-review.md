# Live E2E and Infrastructure Risk Review

## Executive Result

A live end-to-end payment-switch execution across **APISIX → Temporal → TigerBeetle** could not be completed in the current sandbox because the Docker executable and daemon are unavailable, and the APISIX, Temporal, and TigerBeetle listener ports are not open. This is recorded as **blocked**, not passed. PostgreSQL is reachable on `127.0.0.1:5432`, but that alone cannot establish a payment-flow success.

| Component | Probe | Result |
| --- | --- | --- |
| Docker runtime | Docker executable and server | Unavailable: executable not found |
| APISIX data plane | `127.0.0.1:9080` TCP probe | Closed: connection refused |
| APISIX admin API | `127.0.0.1:9180` TCP probe | Closed: connection refused |
| Temporal frontend | `127.0.0.1:7233` TCP probe | Closed: connection refused |
| TigerBeetle published port | `127.0.0.1:3002` TCP probe | Closed: connection refused |
| PostgreSQL | `127.0.0.1:5432` TCP probe | Open |

The reproducible evidence is saved in `audit/artifacts/live-platform-probe.json`, generated by `scripts/live_platform_probe.py`.

## Infrastructure Risk Review

The post-remediation static Compose audit reports **zero critical findings**, **59 high findings**, and **22 medium findings**. The remaining findings are grouped below by operational consequence rather than treated as independent cosmetic warnings.

| Priority | Category | Count | Assessment | Recommended disposition |
| --- | --- | ---: | --- | --- |
| P0 | Undefined service hosts | 3 high | Settlement services point to `mojaloop-central-settlements`, which is not defined in the affected manifests. A payment path can fail at runtime even if containers start. | Add the required service to the same Compose project or replace the URL with a verified deployed service-discovery name. Do not substitute a placeholder host. |
| P0 | Required secrets without startup guards | 18 high | Services interpolate credentials but manifests do not prove that startup fails when values are absent. This can produce partial, misleading deployments. | Add `${VAR:?VAR must be set}` guards or an equivalent preflight entrypoint for every required secret. Keep credentials outside version control. |
| P0 | Weak static secrets | 22 high | Development and deployment manifests contain predictable passwords and tokens, including admin credentials and Redis/Postgres passwords. | Replace with required environment or secret-file inputs; rotate any value used outside an isolated disposable environment. |
| P1 | Missing bind sources | 16 high | Some manifests still reference paths that are absent in the selected Compose file’s relative context, notably ELK host Docker paths. | Make host mounts environment-specific and explicitly optional where appropriate, or provide tracked service-local assets. Do not silently mount empty substitute directories. |
| P1 | Missing health checks | 22 medium | Temporal, TigerBeetle, APISIX, Keycloak, Permify, Redis, and Postgres instances lack readiness checks in several manifests. Dependencies may start before they are usable. | Add service-native readiness probes and use conditional `depends_on` where Compose supports it. |

## Fixes Applied During This Review

The remaining critical Compose collision was removed by changing the unified central-ledger host publication from `3000:3001` to `3003:3001`, preserving the web portal’s host port 3000. The first-pass corrections for APISIX, Prometheus, Grafana, Nginx, Logstash, and Filebeat paths remain in place. The ELK Logstash/Filebeat configuration files are now tracked.

These changes were statically validated, but they were not runtime-proven because Docker is unavailable in the current environment.

## Required Live Run Once Runtime Is Available

The live run should be performed in an environment with Docker access and the required secrets. It must first start the selected unified manifest, wait for readiness of PostgreSQL, Redis, APISIX, Temporal, and TigerBeetle, and then execute a non-production payment fixture. The evidence must include the APISIX request and response, the Temporal workflow ID and terminal state, the TigerBeetle transfer or batch result, and the PostgreSQL transaction record. Any missing service, timeout, authentication failure, or absent ledger record must fail the run.

A successful HTTP response from APISIX alone is insufficient. The flow is only successful when the request reaches the intended backend, the Temporal workflow reaches a terminal success state, TigerBeetle confirms the ledger operation, and the persisted transaction agrees with the external result.
