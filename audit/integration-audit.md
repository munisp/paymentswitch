## Keycloak: BROKEN

There are multiple executable touchpoints for Keycloak (live readiness probing, APISIX OIDC plugin config, Go/Python clients, Kubernetes secret wiring), but the primary web-portal auth flow depends on a custom OAuth portal and SDK paths that do not match Keycloak OIDC endpoints. Realm/realm-name and DB credential contradictions, lack of deterministic realm import/bootstrap, insecure defaults, and success-shaped seed fallbacks indicate the integration will not reliably authenticate users in production without manual fixes.

### Gaps

| Severity | Gap | Evidence | Production Impact | Required Fix |
| --- | --- | --- | --- | --- |
| **CRITICAL** | Web-portal OAuth SDK uses non-Keycloak endpoints; flow likely incompatible with Keycloak OIDC | `server/_core/sdk.ts:33-36; server/_core/env.ts:31-39` | Authorization code exchange and userinfo retrieval will fail against Keycloak, breaking login. | Replace custom EXCHANGE_TOKEN_PATH/GET_USER_INFO* with standard Keycloak OIDC endpoints: /token and /userinfo under ${KEYCLOAK_URL}/realms/${KEYCLOAK_REALM}/protocol/openid-connect. Implement code_verifier/code_challenge if using PKCE and map 'sub' to internal user. |
| **CRITICAL** | Success-shaped seed fallback for Keycloak health/status | `server/routers/middlewareRouter.ts:319-332` | UI and monitoring can report Keycloak as healthy with rich metrics even when it is unreachable, masking outages and enabling production paths to proceed under false assumptions. | Remove seed fallback for production; when live probe fails, return explicit unhealthy status and non-200 where appropriate. Gate any demo data behind NODE_ENV!=='production' flags. |

## TigerBeetle: PARTIAL

Executable call paths exist in Go services to perform real TigerBeetle operations (e.g., CreateAccounts via internal client) and deployment manifests pass TB addresses. However, multiple production blockers and success-shaped fallbacks undermine reliability: Kubernetes NetworkPolicies allow only port 3000 while Go services are configured to connect on 3001; HTTP gateway health checks are implemented without any deployed gateway; docker healthcheck always reports healthy; docker/k8s bootstraps often omit required TigerBeetle data-file formatting; and UI/middleware endpoints silently return seed data when live checks fail.

## PostgreSQL: PARTIAL

## APISIX: PARTIAL

Executable clients and configs exist, and APISIX containers are defined with a working /apisix/status healthcheck. A live Admin API client is implemented in server/lib and used by tRPC routes. However, multiple boot blockers and contradictions prevent secure, working production use: the Admin API is bound to 127.0.0.1 while other services call http://apisix:9180; the openid-connect plugin is referenced by routes but not enabled in the APISIX plugin list; required secrets are not injected; and UI/server paths silently fall back to success-shaped seed data, masking failures.

### Gaps

| Severity | Gap | Evidence | Production Impact | Required Fix |

## Fluvio: PARTIAL

Executable elements exist but are incomplete and inconsistent. There is a real Fluvio SmartModule (Rust) and services referencing native Fluvio clients (Go POS gateway, Python consumer).
